## 0. 结论先行（TL;DR）

**不存在需要逆向的"自定义指令编码"——至少在这个镜像里一条都没有。**

`<unknown>` 的 62% 是三件互不相干的假象叠加：

1. **工具默认特征集**：`llvm-objdump --triple=riscv64` 默认只开 **RV64I**，`C`（压缩指令）和 `M`/`A` 都没开。仅加 `--mattr=+m,+a,+c,+zicsr,+zifencei`，代码区 **100.00%** 全部解码，`<unknown>` 归零。
2. **扫掠起点错**：可执行段 `p_offset=0` 与 ELF 头重叠，段基址 `0xffffffff92fff000` 上放的是**原镜像自己的 ELF 头**，`e_entry = 0xffffffff93000000 = 段基址+0x1000`。从段基址线性扫掠会让 LLVM 从 `7f 45 4c 46` 开始解码且**永远不会重新对齐**到 `0x93000000` 的代码网格。
3. **把 rodata 当代码扫**：段尾 `0x9300c000`–`0x9300e000`（8 KiB）是 libos 的源文件路径和断言字符串（可打印率 90–96%）；"段熵 6.69、明文代码"这个判据其实混合了代码（熵 7.02）和字符串（熵 5.26），整段实测熵 6.72。

> **答案其实一直写在文件头里**：这 12 个镜像的 `e_flags` 全部等于 `0x1`，即 `EF_RISCV_RVC`（ELF psABI 规定的"C 扩展已启用"标志位）。`llvm-objdump` **不读 e_flags 来决定特征集**，所以它对一个自己声明了 RVC 的目标仍然逐条吐出 `<unknown>`。这一条就是"62% 未知"的全部原因，见 §2 H4。

| 口径 | 样本量（token） | 默认(RV64I) | `+m,+a,+c,+zicsr,+zifencei` |
|---|---|---|---|
| 整段 61,440 B（含头页+rodata） | 18,706 | 37.84%（11,627 未知） | 96.63%（631 未知） |
| **代码区 48 KiB**（段内偏移 `0x1000–0xd000`） | **16,162** | **42.43%**（9,305 未知） | **100.00%（0 未知）** |

原先报告的"18,706 条 / 62% unknown / 653 对中 30%"在本文流水线上被**精确复现**（18,706 / 11,627 unknown = 62.16%），所以下面的差异不是样本不同，而是解码参数不同。

## 2. 假设与验证

四个候选假设逐一过。判据用自洽性，不看"像不像"。

### H1 —— 是标准 custom-0/1/2/3（0x0B/0x2B/0x5B/0x7B），只是 LLVM 不认

**证伪。** 三条独立证据：

1. **代码区计数为 0**：对段内偏移 `0x1000–0xd000` 的所有指令边界，`w & 0x7F ∈ {0x0B,0x2B,0x5B,0x7B}` 出现 **0 次**（任何长度）。
2. **整段仅 3 次，全在 rodata 且是 ASCII**：
   - `0x9300d334` `w=0x694c202b` → 字节 `2b 20 4c 69` = `"+ Li"`（字符串）
   - `0x9300d91f` `w=0x06343f0b`、`0x9300dc55` `w=0xad00000b` → 同一字符串表里的字节
3. **在 13.6 MB 的 img09 上做强验证**：前 10 MB / **3,487,079 条指令覆盖率 100.00%（仅 13 个未知，全在开头 ELF 头页）**，`0x0B/0x2B/0x5B/0x7B` 出现 **0 次**；这 4 个 opcode 只在最后 2.9 MB（`0xa00000` 之后）出现，合计 `0x0B` 2,947 次 / `0x2B` 3,617 次 / `0x5B` 3,142 次 / `0x7B` 2,771 次，且与 `0x77`(6,450)、`0x7F`(4,911)、`0x6B`(4,156)、`0x3F`(3,274)（RISC-V 规范里**未分配**的 opcode）以同一量级出现在同样的两个 2 MB 桶里。

   未分配 opcode 与 4 个 custom opcode 以同量级均匀出现，是**随机数据**的签名；真实 ISA 扩展会强烈偏斜到少数几个 opcode 上。

**反面还有一个统计学判据**：这 4 个值合计只占未知 token 的 10% 左右，且不随任何假设系统性变化；若它们是真正的指令，编码分布应集中在极少数 funct3/funct7 组合上（像 `0x33` 那样只有 f3∈{0,5,7} 三种），而实测散布在所有功能位上。

### H2 —— 是标准指令但用了非标准字段位置

**证伪。** 用 `auipc + <consumer>` 的地址自洽性判定，代码区 855 对：

| 指标 | 数值 |
|---|---|
| `auipc` token 数 | 855 |
| 找到消费者（`addi`/`addiw`/load/store，含压缩形式） | 855（100%） |
| 目标落在文件内 PT_LOAD 段 | 715（83.6%）— RX 221 / RW 494 |
| 目标落在数据段 BSS 尾部 | 140（16.4%）— 全部在 RW 文件末尾之后 `0x0000–0x29a0` 范围内 |
| **目标 = 一条可打印字符串的首字节** | **150（17.5%）** |

140 个"未映射"目标全部连续紧贴 `0xffffffffa301f000`（RW 文件末尾）之后的 `0x1cb8 … 0x29a0`，这是该 ELF 没有带出的 BSS 尾部，不是随机地址。**因此 855/855 = 100% 的 `auipc+addi` 都落在程序自己的段内**，字段位置完全标准。

命中的字符串正是任务里给出的判据，逐字复现：

```
0x93001146: 0000b597  auipc a1, 0xb          ; a1 = PC + 0xb000 = 0x9300c146
0x9300114a: 09258593  addi  a1, a1, 0x92     ; a1 = 0x9300c1d8
0x9300c1d8:                                   "index < MPU_COUNT"
0x9300115c: → 0x9300c198  "/gpu_drv/uproc/os/libos-v3.1.0/src/kernel/mm/softmmu_core.c"
```

> 注：`auipc` 的立即数在 objdump 里是**未移位的 20 位字段**，必须 `<<12` 才是位移量。先前统计得到"30% 落在段内"，一部分原因就是漏了这次左移，再加上只匹配 RX 段（而 494/715 个合法目标指向数据段）。修正后是 83.6% 文件内 + 16.4% BSS 尾部。

### H3 —— 是"变长前缀"扩展

**证伪。**

- 代码区编码长度直方图只有 2 字节和 4 字节两种：全量 token `{2 字节: 9,256, 4 字节: 6,906}`，**没有任何 6 字节 / 8 字节 token**。
- ≥48 位编码要求 `b[1:0]==11` 且 `b[4:2]==111`，即首字节低 7 位为 `0x1F/0x3F/0x5F/0x7F`。代码区这类字出现 **0 次**。
- 清单里那些"一条 `<unknown>` 占 16 字节"的行全部位于头页或 rodata —— LLVM 把无法解码的**数据块**按 16 字节一行打出来（`ffffffff93000021: 557533ff218eaa00…`），不是一条超长指令。

### H4 —— 是标准 RISC-V 的罕见指令（Zbb/Zbs/A/压缩）被误标 unknown

**成立。这就是全部答案。** 分两步：

**第一步，压缩指令（C）解释 99.47%。** 代码区 9,305 个未知里 9,256 个是 16 位。只加 `--mattr=+c`：

| 特征集 | 未知 token | 覆盖率 |
|---|---|---|
| 默认（RV64I） | 9,305 | 42.43% |
| `+c` | **49** | **99.70%** |
| `+m,+a` | 9,256 | 42.73% |
| `+m,+a,+c,+zicsr,+zifencei` | **0** | **100.00%** |
| 最大集合（`+f,+d,+b,+zbb,…,+zcmp`） | 0 | 100.00% |

**第二步，M 扩展解释剩余的 49 个**（`0x33/0x3b` + funct7=0x01 → `mul/div/rem` 族），加 `+m` 后归零。`A` 在 img00 代码区**没被用到**（`+m` 单独就够），`F/D` 也不需要，`B/Zbb` 完全不需要（`+imac` 与 `+imac+b` 数值完全相同：631/631）。

**为什么默认不给？** 这是本次最实用的一条：`llvm-objdump --triple=riscv64` 的默认 `FeatureBits` 是**裸 RV64I**，`C`/`M`/`A` 一律关闭。实测探针：

```
0000000000001000: 000100f3 <unknown>        # rd!=0，确实非法
0000000000001004: 00100073 ebreak
0000000000001010: 00000013 nop
000000000000101c: 027302b3 <unknown>        # mul  —— 默认不认 M
0000000000001030: 4515     <unknown>        # c.li —— 默认不认 C
0000000000001034: 8082     <unknown>        # c.ret
```

**更有决定性的一条：这个判断本来就不需要猜。** 全部 12 个镜像的 ELF 头 `e_flags` 都等于 `0x1`：

| 镜像 | `e_flags` | 含义 | float ABI |
|---|---|---|---|
| img00–img11（全部 12 个） | `0x1` | `EF_RISCV_RVC` — **声明已启用 C 扩展** | 0（soft-float） |

也就是说，产出这些镜像的工具链（`-march=rv64imac` 或类似）把"C 已启用"写进了 psABI 规定的标志位；`llvm-objdump` 在选特征集时**并不读 e_flags**，于是它对着一个自称 RVC 的目标逐条报 `<unknown>`。这是 H4 的权威证据，而不是统计推断。

### 2.1 自洽性检验（三个判据的实测数字）

**(a) 直接跳转目标是否落在指令边界上**（代码区内、源也必须在代码区）

| 解码 | 直接目标数 | 落在边界 | 比例 |
|---|---|---|---|
| 默认 RV64I | 2,024 | 2,024 | **100.00%** |
| `+c` / `+m,+a,+c` / 最大 | 3,089 | 3,089 | **100.00%** |

**必须诚实说明这条判据在这里的局限**：LLVM 的步进长度只由原始比特位决定（`(b0&3)!=3` → 2 字节，否则 4 字节），所以**指令边界网格与特征集无关**。因此这个比例在两个特征集下都必然是 100%，它**不能**用来区分"开不开 C"。

它真正验证了两件事：

- 最大特征集解码与网格完全自洽（3,089/3,089，没有一处"分支跳到半条指令中间"）。
- **3,089 个目标里有 1,469 个（47.3%）落在 `≡2 (mod 4)` 的地址上**。纯 RV64I 的代码所有指令都是 4 字节对齐，不可能出现这种情况 → **16 位指令确实存在，且这个网格是对的**。这是本报告里关于"必须开 C"最硬的一条量化证据。

之前把整段（含 rodata）都算进去时这个比例是 96.46%，那 114 个"不在边界"的目标**全部**是 rodata 里的数据字节被误当成分支解出来的（例：`0x9300c0e2 → 0x9300c76a`），不是代码问题。

**(b) 函数序言 / 尾声配对**

| 解码 | `addi sp,sp,-N` / `c.addi16sp` | `ret` / `c.jr ra` / `jalr x0,0(ra)` |
|---|---|---|
| 默认 RV64I | **6** | **1** |
| `+m,+a,+c` | **185** | **227** |

这是 H4 最强的独立旁证：一个约 46 KiB 的裸机内核，默认解码只看到 6 个栈帧和 1 个返回；开启 C 后立刻出现 185/227 —— 数量级恢复正常。比值 227/185 > 1 是因为尾调用 `j` 跳板与 noreturn 路径，本判据只当"数量级合理性"用，不当精确配对。

**(c) `auipc+addi` → 字符串/数据**：见 H2，855/855 = 100% 落在程序自己的段内，150 对精确命中 libos 断言字符串首字节。

### 2.2 顺带发现：真正的"自定义"在哪里

自定义不在 opcode，在 **CSR 编号**。代码区数值型 CSR 使用统计：

| CSR | 次数 | 类别 |
|---|---|---|
| `0x000`,`0x002` | 1 / 5 | 标准 user（`fflags`/`frm` 等） |
| `0x5c0` | 2 | **非标准** |
| `0x5ca` | 16 | **非标准** |
| `0x5cb` | 16 | **非标准** |
| `0x5cc` | 13 | **非标准** |
| `0x5ce` | 9 | **非标准** |
| `0x5cf` | 14 | **非标准** |
| `0x5d0` / `0x5d1` | 4 / 4 | **非标准** |
| `0x5d7` | 1 | **非标准** |
| `0x8d0` | 2 | **非标准**（`0x800–0x8FF` 只读自定义区） |

符号型 CSR 是标准 S 态集合：`sstatus`(24)、`sepc`(15)、`sscratch`(14)、`stval`(6)、`scause`(5)、`sie`(4)、`sip`(1)、`satp`(1)、`stvec`(1)、`scounteren`(1) —— 所以 hart 跑在 S 态，`0x5xx`/`0x8xx` 是 NVIDIA 加的 S 态私有 CSR 窗口。

启动存根（`0x93000000`，全部正常解码）把语义透露得相当清楚：

```
93000028: li   t3, 8
9300002a: csrw 0x5ca, t3        ; ← 选择子 / 索引      = 8
9300002e: csrw 0x5cc, t4        ; ← 基址               = 0x93000000
93000034: csrw 0x5ce, a0        ; ← 大小/上界          = 0x1000
93000040: csrw 0x5cf, t1        ; ← 属性/权限          = 0x40028
93000048: csrw 0x5cb, t4|1      ; ← 带标记的上界       = 0x93000001
93000052: csrs satp, t0         ; satp |= 0xf000000000000000
```

`0x5ca` 当选择子、`0x5cb..0x5cf` 当窗口寄存器的用法，与字符串里的 `index < MPU_COUNT`、`softmmu_core.c`、`identity.c` 完全对得上。
另有 `0x5c0` 在 `ecall` 陷入后立即写入、保存上下文时读回（`0x930037e8` / `0x9300386c`），疑似陷入/上下文 CSR；`0x8d0` 在一个循环里以 `+0x40` 步进写入（`0x9300069c` / `0x93000710`），疑似 softmmu/MPU 表项的窗口式批量寄存器。
**以上 CSR 语义全部 `[未确认]`** —— 只有"编号非标准、用法与 MPU 窗口一致"是实测的。

## 3. 结论

**能解码到多少 %**

| 范围 | 样本 | 默认 | 正确特征集 |
|---|---|---|---|
| img00 代码区（48 KiB，段内 `0x1000–0xd000`） | 16,162 token / 46,135 B | 42.43% | **100.00%（0 未知）** |
| img00 整段（61,440 B） | 18,706 token | 37.84% | 97.85%（403 未知，全部是头页+rodata 的真实数据） |
| 全部 12 个镜像（见 `reports/nvrx-coverage.csv`） | 7,881–4,505,054 token | 37.68%–46.59% | 代码页 97.93%–99.86% |
| img09（13.6 MB，最大镜像） | 4,505,054 token | 41.57% | 97.58%；前 10 MB / 3,487,079 条指令 **100.00%** |

**是否需要给出映射表**：**不需要。** 没有需要映射的自定义 opcode；需要的是正确的 `-mattr` 和正确的扫掠起点。等价于一句话：

```
llvm-objdump -d --triple=riscv64 --mattr=+m,+a,+c,+zicsr,+zifencei <elf>
```

**还缺什么**

1. `0x5c0 / 0x5ca–0x5cf / 0x5d0 / 0x5d1 / 0x5d7 / 0x8d0` 的精确语义 —— `[未确认]`。只能从使用模式推测（MPU 窗口描述符 + 一个陷入上下文寄存器 + 一个批量窗口寄存器）。
2. img09 尾部约 2.4%（108,963/4,505,054）的 `<unknown>` 归属。证据强烈指向"数据嵌在 `.text` 里"（未知质量 89,760 集中在覆盖率 50–90% 的页；最差的页 99.7% 可打印 = 字符串表；`0x0B` 等未分配 opcode 只在这两个 2 MB 桶里出现），但**没有逐字节证明**，标 `[未确认]`。
3. 函数边界/符号级语义（哪些地址是函数入口）。本工具的可达性分析只从 `e_entry` + `lui/addi/auipc`→`jr` 常量折叠出发，在 img00 只覆盖 153 条指令（1.0% 字节）—— 因为绝大部分函数是通过数据段里的函数指针表调用的，需要额外的跳转表解析。

**被证伪的假设（负面结果同样记录）**：custom-0/1/2/3 编码（H1）、非标准字段位置（H2）、变长前缀扩展（H3）。三条都不是"没找到证据"，而是有反例数字。

## 4. 后续可做

1. **把解码参数固化进流水线，并把扫掠起点改成 `e_entry`。**
   现在 `_xr.elf` 造出来的 `.text` 从段基址 `0xffffffff92fff000` 开始，那 4 KiB 是原镜像自己的 ELF 头，LLVM 会从 `7f 45 4c 46` 开始解码且**不会重新同步**，`0x93000000` 之前的 5 个未知 token 就是这么来的。验收判据很明确：**代码区必须 0 个 `<unknown>`，且 3,089 个直接跳转目标 100% 落在指令边界上**。建议同时加 `-M no-aliases`，避免 `8faa → mv`、`8082 → ret` 这类别名把 16 位指令藏起来（本次统计压缩指令占比 57.36% 只能靠编码长度算）。

2. **给私有 CSR 建一张可核对的表。**
   写一个提取器：对每条 `csr*` 指令记录 `(pc, csr 号, rd, rs1, 紧邻的常量)`，把 `csrw 0x5ca, X` 的 `X` 当"选择子序列"，把随后对 `0x5cb..0x5cf` 的写入当"窗口字段"，按选择子分组聚合。然后用 `identity.c` / `softmmu_core.c` / `sbi.c` 的断言站点（本报告已能定位 150 处字符串引用）反查每组的取值范围与用途，最后与开源 libos / nouveau 的 `nvkm` 侧代码对照。这是唯一能把 `[未确认]` 变成"已验证"的路径。

3. **把 img09 的 2.4% 残余定性，并把"数据还是指令"变成可判定的统计量。**
   已有两个现成判据：页覆盖率（`cov<90%` 的页几乎必然是数据，本工具已输出 `pages` 数组）、以及 opcode 分布的 χ² 检验——数据字节的 opcode 分布由字节直方图决定，真实指令则强烈偏斜（对照 `0x33` 只有 3 个 funct3 值）。再加一步：把全部 `--mcpu=<vendor>`（`sifive-*`、`spacemit-*`、`xiangshan-*`、`andes-*`、`syntacore-*` 等 60 个）与全部 `-mattr=+<ext>` 枚举一遍，确认没有哪个未公开的扩展能把残余变成合法指令——**预期结果仍是 0**（因为 custom opcode 在纯代码区已经 0 次），但这能把"我们试过了"写成结论而不是猜测。

## 附录 A：`tools/nvrx.py` 用法

```
# 段几何 / 截断检查
python nvrx.py info  <elf>

# 覆盖率 × 特征集矩阵 + 未知指令分类 + 三项自洽性检验
python nvrx.py analyze <elf> [--json out.json]
python nvrx.py analyze <elf> --start 0x1000 --length 0xc000    # 只分析代码区
python nvrx.py analyze <elf> --mattr +m,+a,+c                   # 指定单一特征集

# 递归下降（自 e_entry + lui/addi/auipc→jr 常量折叠）
python nvrx.py sweep <elf> [--show 20]

# 批量：多个镜像的覆盖率表 -> CSV
python nvrx.py batch "../img0*_0x*.elf" --csv coverage.csv

# 导出原始段字节（只读源文件，新建 .bin + .json）
python nvrx.py extract <elf> out.bin [--seg N] [--vaddr 0x..]
```

`analyze` 输出字段：`total/unknown/coverage_pct`（整段线性扫掠）、`reach`（可达性）、`unknown_profile_all`（opcode / `(opcode,funct3)` / `(opcode,funct7)` / 长度直方图 + 样本十六进制）、`branch`（跳转目标对齐率 + 反例）、`auipc`（`auipc+consumer` 目标落点统计）、`func`（序言/尾声）、`pages`（每 4 KiB 页的覆盖率与可打印率，用来切代码/数据）、`isa`（扩展使用画像）。

已知局限：不做符号级函数识别；可达性只认 `lui/addi/addiw/auipc` 常量折叠，不解析数据段里的函数指针表；`llvm-objdump` 会把数据区打印成长字节串（`...` 省略），这些位置不计入 token 数。所有不支持的情形都会在 JSON 里显式留空，不会静默给 0。
